**让用户输入真实公告/报告及可用资料，系统自主查证并批量生成有来源、有代码依据的完整 VulnGym Entry；证据不足时明确保留待复核状态，帮助研究者高效扩充数据集。**

主交付是可运行的 **T2 CLI/批处理工具 + 完整数据 JSONL + 可读证据与自评 + 源码/README + 真实开发记录 + 简短演示**。不要求先做 Web UI。CLI 是我们的产品选择，不是导师限定的唯一形式。

T2 完成度高，指实际可用、质量可信、场景有代表性、限制说明完整，**不等于 Issue 关闭多、运行久、样本数多或自动通过率高**。也不能用“导师允许不确定”把核心抽取能力降格成一律弃答。

## 4. T2 的产品契约

### 输入和范围

- 主支持对象为 GHSA/公告资料包及目标仓库；说明支持的输入格式、缓存准备和命令，不把尚未实现的“任意 URL 一键抓取”写成已有功能。
- 可用资料包括公告、引用文档、issue/PR、patch 和固定版本源码。记录取得了什么、缺了什么，不能假设每份报告都有修复补丁或唯一父提交。
- fix commit 不是自动等同于受影响 commit。唯一父提交只是可验证场景之一；合并、回移、多版本或版本不明要说明裁决依据或退出为待复核。
- 样例优先包含信息不完整的真实应用报告，不用只有充分 patch/链路的 Linux 披露来代表泛化能力。
- 开发时看过公开标注的案例须标为开发/回归案例，不能随后宣称为未见盲测。任何隐藏答案仍不得进入生产路径。

### 输出和状态

1. 支持对输入列表逐项出具任务结果；一个报告可对应零条（明确 defer）或一条/多条数据。报告数、任务数、Entry 数分开统计，不假设永远一对一。
2. 完整数据进入 `entries.jsonl`，符合当前 [SCHEMA.md](../SCHEMA.md) 的实际兼容契约，包含来源、标识、仓库/commit、标题/分类、EP/CO 的 file/line/code 及 trace 等字段。
3. **机器产出 `verify=0`**；AI 自检、T1 correct、D3 accept 均不能冒充人工验证。
4. 必填字段无依据且 schema 不允许缺失时，输出独立任务/复核记录，保留部分证据，不塞入虚假值或非法 Entry。schema 容许的 missing/空 trace 也必须说明原因；不为凑完整而编链路。
5. 提供可读的逐字段证据/待复核说明；T1 的 `validation.jsonl` 是现有辅助报告，不是所有 T2 语义质量的唯一裁判。
6. `manual_review` 表示工作流终态；`incorrect` 表示某检查提出错误；`uncertain` 表示未证实。三者不得混成“成功”或“失败”。已指出的错误应核查、修正或从“高质量自动产出”中明确排除。
7. 不改目标仓库来修复原漏洞；只在有依据时修正本工具生成的数据，并保留前后差异及重新验证记录。

### 自动化真实性

当前 exact replay 可复现既有选择，但 **回放已人工制备的答案不等于对新报告自主抽取**。主线需补齐/展示不依赖逐题手写 EP/CO、固定 response 的实际生产入口（可用声明清楚的模型/规则方案）；对未预编排的新报告进行实跑。离线回放保留作回归证据，两者分别标识。

## 5. 不确定性及人工复核策略

这是质量策略，不是为了提高通过率的豁免：

| 类型 | 应怎样处理 | 怎样计入自评 |
| --- | --- | --- |
| 信息不足/来源冲突 | 给出已知事实、冲突/缺失点、需要补什么 | 合理弃答，单列比例和理由 |
| 多种合理 EP/CO/trace | 展示候选角色和语义依据；不能唯一裁决则待复核 | 不因不同于单一参考而直接判错 |
| 检查器能力未实现 | 明说 `unsupported_check` 等能力缺口 | 工程限制，不包装成“该报告本来不可判断” |
| 预算耗尽/读取失败/格式错误 | 输出可诊断的运行状态，避免静默丢任务 | 执行失败/资源限制，与语义不确定分开 |
| 有反证或确定错误 | 标明冲突字段，核查、修正或退回 | 错误不能计入可靠自动产出 |

每条待复核记录至少含：任务/版本标识、候选字段、证据来源、未知/冲突点、缺失信息、下一步人工动作和当前状态。人工尚未签署就写“待复核”，不能把整理好的清单称为完成复核。

人工复核无需替 AI 把所有样本强行标完；但需对代表性产出做实质评价，证明系统既能得到有价值结论，也能在该停的时候停。人工修正必须和原始自动输出分开保存。
